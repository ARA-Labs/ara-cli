1. Summary

  • Each researcher works in a private fork of one seed ARA. A researcher is a person or an agent.
  • When a result is ready, a runner stops the fork and freezes it.
  • The runner publishes the frozen fork as a contribution. A contribution does not change after publication.
  • Peers can read, reproduce, challenge, or import a contribution before canonical integration.
  • One integration project manager (PM) merges selected contributions into canonical logic/. Competing interpretations stay visible.
  • Lara can recheck the numbers and the arguments of selected claims. This step is optional.
  • ara-cli gets two changes only: the ara snapshot command (plan 01) and a merge fix for peer feedback (plan 04). Plan 01 proposes a private jj-lib version store behind the command. Agents never see jj. This part is pending re-approval.
  • Publication, participant authority, community views, and Lara calls stay outside the CLI. The runner (ara-eval) does these tasks.

2. The problem

Four workers fork the same seed ARA. The research question is: "Why does method M improve task T?"

WorkerTask
ATests an ablation of the mechanism of M.
BTries an alternative implementation.
CReproduces the result of A.
DLooks for counterevidence against the interpretation of A.

The current tools fail at four points:

  1. 1. Duplicate workB cannot see the ablation of A until a person merges the fork of A. A merge after the work does not prevent the duplicate run.
  2. 2. No exact versionThe fork of A continues to change. No object holds its knowledge, code, and evidence under one identity. Thus C has no stable target.
  3. 3. Lost alternativesCanonical logic/ holds one current interpretation. If A and D disagree, the other interpretation stays only in a private fork.
  4. 4. Unclear authorityThe artifact lock serializes CLI writes in one checkout. It does not sync different checkouts. It does not decide who can change canonical logic/.

Agora solves the visibility part with a shared contribution graph. This design adds three items that a graph of commits does not supply:

  • Typed knowledge. Claims have conditions, falsification criteria, and dependencies. Trace nodes record questions, experiments, dead ends, and pivots.
  • Explicit source references. Each merged entry records its source fork and revision.
  • Audited mutable logic. Each change to canonical logic/ keeps a before/after history and an owner session.

Thus a worker can get the dependencies of one hypothesis. The worker does not have to read a full log.

3. The end-to-end flow

  1. Worker: Read the question, the dependencies, the claims, and the failed attempts with ara read commands.
  2. Runner: Refresh the briefing. Post an intention. 02
  3. Worker tools: Run the experiment in an isolated code workspace.
  4. Continuity writer: Record the result with ara apply and session history.
  5. Runner: Stop all writers. Run ara snapshot create, then ara snapshot export. 01
  6. Argument producer and runner: Optionally, write a Lara argument and run the check. 03
  7. Runner: Freeze the package. Publish the contribution. Announce it. 02
  8. Peers: Read, reproduce, or challenge. Optionally, import it into their own fork. 04
  9. Peers: Publish a follow-on contribution. Keep the parent identities.
  10. Integration PM: Merge exact versions. Acknowledge external files. Resolve conflicts. 02
  11. Runner: Publish an integration receipt. Refresh the briefing.

6. Design parts, reasons, and Agora

Blue column: what the design does. Green column: why. Orange column: what Agora does for the same function.

6.1 Private forks and one canonical writer README, D2

What

  • Each participant writes only to its own fork.
  • Only the integration PM changes canonical logic/.
  • File-system permissions and the runner tool policy isolate the forks.
  • The artifact lock is not access control. Same-checkout writers stay supported if they cooperate.

Why

  • Many writers in one checkout do not isolate experiment code. They also do not keep separate interpretations.
  • One canonical writer makes each canonical change auditable.
  • Raw contributions are visible before integration. Thus a slow PM does not block peers.
  • D2: change this decision only if evidence shows a bottleneck.

Agora

  • Agora has no canonical synthesis document.
  • Each worker publishes commits into one shared, append-only Git graph. The graph is the record.
  • The "best" result is a view (leaders). It is not a merged document.
  • Workers never edit a published node.

6.2 ara snapshot: an exact offline capture 01, D4

Two command shapes exist in plan 01. The approved shape is one command with a directory output. The revised shape (pending re-approval and a spike) adds a private version store and three subcommands. The capture rules are the same in both.

# Revised (pending re-approval)
ara -C ./forks/a snapshot create --json                      # capture + record in the store
ara -C ./forks/a snapshot list --json                        # recorded fingerprints, in parent order
ara -C ./forks/a snapshot export 3b9c…e41a --output ./packages/a-0007 --json

# Approved baseline (and the fallback if the spike fails)
ara -C ./forks/a snapshot --output ./packages/a-0007 --json

packages/a-0007/
├── ara/            # every captured file, with captured bytes and modes
└── snapshot.json   # manifest: fingerprint, per-file sha256/size/mode, diagnostics

What

  • Capture (approved): take the artifact lock. Reject a pending transaction. Read each nonprivate file. Exclude .git/, .ara/, and temporary paths at all depths. Reject symlinks.
  • Export (approved publication steps): copy the files into <output>/ara/. Write snapshot.json. Verify the copy and read the source again.
  • Publish the output with an atomic, no-replace operation.
  • If the source changed, expose nothing and return stale_snapshot_input.
  • Revised: create also records the capture in a store at .ara/vcs/, built on jj-lib. create returns recorded: false if the fingerprint is already there.
  • Revised: ara decides what is captured. jj-lib only stores the captured trees, their order, and its operation log.
  • Revised: no jj command, term, identifier, file, or error appears in CLI output, agent docs, or skills. The store has no .jj/ directory and never reads user jj or Git configuration.

Why

  • The runner is Python. If it copies and hashes the fork itself, it must copy the core capture rules.
  • A small difference makes the published fingerprint differ from the fingerprint that ara merge sees. One command keeps one implementation.
  • The fingerprint does not include file modes. Thus the manifest records modes.
  • D-S2: no --source-key. The envelope owns source identity.
  • D-S3: diagnostic errors do not stop capture. Publication policy decides.
  • The lock stops only cooperating CLI writers. The caller must stop direct writers. The second read only detects changes.
  • A core fix is necessary: load_complete can read nested .ara/ or .git/ before it excludes them.
  • Why a store: plan 02 keeps every predecessor snapshot, because a later import uses the last imported revision as its base. Directory-only output keeps many near-identical full copies. The store keeps one copy of unchanged contents and the order of the snapshots of one fork.
  • Why not a Git commit as the capture: a commit omits ignored and unstaged files. It also ignores the ara lock and transaction journal, so it can record a half-applied write.
  • The store is a private, derived record. The knowledge files stay authoritative. If .ara/vcs/ is deleted, the history is lost but no artifact content is lost. A published package is the publication authority.
  • jj-lib stays in a native-only crate, ara-vcs, behind a small trait. ara-core still builds for wasm. A different store (for example gix) touches only that crate.

Agora

  • Agora freezes work as a Git commit.
  • Code work arrives as a Git bundle. The server validates the bundle and commits it again with a server timestamp.
  • Metadata-only work arrives as JSON. The server writes the commit.
  • Agora App. A lists what a run must pin. v4 reports that the run did not keep evaluator logs and some dependency, data, and model identities.
  • Agora records one commit for each published contribution, not one for each edit. Revised plan 01 does the same (D-S7): it records only on an explicit snapshot create.
Pending decisions on this part (plan 01): D-S4 command shape, D-S6 jj-lib or gix (decided from spike data), D-S7 explicit recording only, D-S8 jj-lib backend, D-S9 retention (keep everything at first), D-S10 read commands at a recorded snapshot (out of scope now). The spike checks that no .jj/ appears, that user jj configuration has no effect, that bytes, modes, and the fingerprint round-trip, and that the build and size cost is acceptable.

6.3 Contribution identity: three different hashes 02, D7

IdentityCoversDoes not cover
Native revisionThe ara.artifact/v1 fingerprint from ara snapshot: nonprivate bytes and paths.File modes, external inputs, attribution.
Payload digestSHA-256("ara.payload/v1\0" || canonical_inventory): all file bytes, sizes, modes, external object digests, the snapshot manifest.Publisher, parents, scientific claim.
Contribution IDSHA-256("ara.contribution/v1\0" || envelope_without_id): payload digest, community, publisher, request, source key, lineage, native pointers.Proof of authorship. (Runner permissions bind the publisher.)

What

  • Parent edges and verification targets use the contribution ID. They never use the payload digest alone.
  • JSON is canonical (RFC 8785). Inventories and parents are sorted.
  • One (community, publisher, request) binds to one contribution ID. An exact retry returns the first receipt. A retry with different content is rejected.
  • Corrections and later checks are new immutable records that point to a contribution ID.

Why

  • A payload digest does not bind attribution, lineage, or a verification target.
  • Two equal payloads can have different authors or parents. Thus they need different IDs.
  • Request idempotency prevents a second contribution after a lost acknowledgment.
  • The envelope stays outside the payload. Thus no hash depends on itself.

Agora

  • Agora uses one Git commit hash for each node. A Git commit hash covers the file tree, the parents, the author, and the message.
  • Thus one hash binds content and lineage.
  • A node also records the author account and a server timestamp. The timestamp makes the order of results checkable.
  • The ARA design separates the hashes because the envelope stays outside the native ARA and large evidence can stay outside Git.

6.4 Publication 02

States: draft → frozen → published. Integration has separate states: pending, imported-with-conflicts, integrated, rejected-for-integration. These are workflow states. They are not native claim statuses.

What

  • Step 1: Stop the worker and its child processes.
  • Step 2: Run ara snapshot create and ara snapshot export (or ara snapshot --output in the approved baseline). Verify the manifest.
  • Step 3: Freeze declared inputs outside the ARA root. Verify their digests. Do not run them.
  • Step 4: Check diagnostics against policy. Bind the result to the intention and the prediction that existed before execution.
  • Step 5: Compute the IDs. The coordinator records the contribution, gives a sequence number, announces it, and then acknowledges.
  • Negative results are published too.

Why

  • Peers must see results before integration. This fixes failure 1.
  • A frozen package is an exact target for reproduction. This fixes failure 2.
  • "Published" means "available and structurally valid". It does not mean "scientifically correct".
  • The announcement is a view of the durable record. It is not a second source of facts.
  • A prediction recorded after execution cannot be labeled a pre-execution prediction.

Agora

  • Agora publishes each attempt at once and never edits it.
  • Successes and failures are both result nodes. 53 nodes have a negative tag.
  • Workers wrote a predicted outcome band before the result by convention, not by rule (400+ descriptions).
  • A SQLite index, rebuilt from Git, serves the views. v4 reports 45 commits missing from the index and one metric cleared only in the database.
  • The ARA design does not copy this split: a rebuild must give the same contributions, corrections, and verdicts.
Timing choice. The ARA research-manager promotes claims only on closure signals. Agora publishes everything at once. This design does both: it publishes raw observations at once, and it promotes claims only on closure signals.

6.5 Briefing and intentions: work visible before a merge 02, plan 14

What

  • The runner builds a briefing from CLI reads over exact snapshots and validated envelopes. It does not parse YAML or Markdown itself.
  • The briefing keeps five types of material separate: canonical facts, own findings, published peer findings not yet integrated, active intentions, stale intentions.
  • Sections: open questions, recent failed attempts, verification gaps and contested results, neglected alternatives, current investigations, integration gaps.
  • An intention names the start snapshot, the question, the action, a code/configuration signature, and (for verification) the target.
  • Intentions are advisory, expire after logical rounds, and are never exclusive.

Why

  • Peers see work in progress. Thus repetition becomes a choice. This fixes failure 1 before the run, not after.
  • Intentions do not block, because independent verification must stay possible.
  • The briefing groups branches by explicit lineage and tags, not by embeddings. The grouping policy has a version and does not change after results are known.
  • A missing snapshot makes the briefing visibly incomplete. An empty frontier never hides a failure.
  • No score changes claim status.

Agora

  • agora analyze gives ranked views: leaders, leaves, unverified results, contested verifications, open hypotheses.
  • During the run, the authors added embedding clusters and a diversity-aware UCB frontier with three slots: exploit, explore known, explore novel.
  • An evidence score counts follow-on work by other accounts.
  • A wip tag is visible and does not change the score. The notes do not describe expiry or a signature for it.
  • v4: 523 equal-score pairs from different accounts (499 without verification and ancestor pairs). Equal scores show convergence, not proven duplicate work.
  • Agora's diversity change modified the views and the prompt together. Thus the effect of the views alone is not known.

6.6 Integration into canonical 02, D5

What

  • The PM imports a frozen snapshot with ara merge --source-key.
  • First import: the base is the shared seed or the declared start snapshot. Later imports: the base is the last imported revision. Keep all predecessor snapshots.
  • A replay of the latest revision makes no duplicates. For an older, already imported revision, the runner returns the stored receipt.
  • A receipt binds the contribution ID, source key, revisions, identity mapping, destination before and after, merge report, and audit session.
  • The runner checks the exit status and unresolved_count. committed: true can mean a partial import.
  • If the PM disagrees with a clean merge, it records an audited logic revision and keeps the competing interpretation.

Why

  • This fixes failures 3 and 4. Alternatives stay recorded. One owner changes canonical.
  • A plain Git merge cannot reconcile native IDs, check protected history, or audit conflicts.
  • A clean structural merge is not scientific agreement.
  • D5: no new expected-revision flag. The PM has exclusive control of the canonical workspace from review to commit.

Agora

  • Agora does not merge.
  • Its 149 multi-parent nodes are citation edges ("builds on"). They are not code merges.
  • The final code is 83 Python modules. Each module imports its parent and applies one change. This is a linear chain of patches.
  • The vault analysis notes that neither Agora nor the ARA paper defines a merge of divergent work.

Code and evidence files during integration

  • The current merger reports each new or changed src/ or evidence/ file as an external_read_only conflict. It permits only ours.
  • Observed with ara 0.1.23: an import with only a new src/worker.py gave exit 1, committed: true, and one unresolved conflict. Replay kept the conflict.
  • The PM acknowledges each such conflict with merge resolve --take ours and an audit reason. The file stays in its contribution. It is not copied into canonical.
  • The receipt records (contribution_id, source_key, native_revision, path, digest) for each external file. Reads use that frozen package and verify the digest.
  • An inherited unresolved conflict has no local choice. The source fork must resolve it and publish a new revision.
  • A knowledge merge never installs code. A synthesis is a new contribution: new workspace, own evaluator, new evidence.

6.7 Verification records 02

What

  • Four kinds: certified numerical recheck (Lara), score reproduction, directional hypothesis test, argument review.
  • Each record names its exact target contribution ID and its conditions.
  • A reproduction binds the actual execution and the raw outputs.
  • Outcomes: confirmed, partial, failed, interrupted, unassessable. All are kept.
  • A new verdict points to the old one. It does not erase it.
  • The current verdict is the latest for each verifier, target, method, and scope, by coordinator sequence (not wall time).
  • The held-out final evaluator stays outside worker access.

Why

  • A verdict without an exact target and conditions cannot be checked again.
  • Separate accounts do not prove independent priors.
  • Reuse counts and endorsements are process measures. They do not make a claim true.
  • Claim promotion follows the native closure procedure only.

Agora

  • A verification node has exactly one target and never targets own work. Results: confirmed, partial, failed.
  • The newest verdict of a verifier replaces its old verdict in the score. Both commits stay.
  • 165 verifications on 95 targets. No reported failures.
  • The evaluator gives bit-identical results on the same hardware. Thus a verification confirms determinism, not the claim.
  • The verifier can see the reported metric. There is no held-out split.
  • Agora App. B: a verdict without target hash, configuration, evaluator identity, and reproduced value "is a coordination hint rather than strong validation evidence."

6.8 Lara numerical and argument checks 03, D3, D8

What

  • For selected claims, an argument producer writes a Lara argument and bindings to exact native sources (source key, native revision, selector, evidence digest).
  • The runner runs a pinned lara check as a separate process. It keeps all inputs, the exit status, and the output.
  • An authorized reviewer, not the producer, attests that the formal statement matches the evidence.
  • A setting registry defines when two experiments share a setting.
  • Later checks are immutable attachments to the original contribution ID.
  • A map revision has its own identity. A new member roster gives a new scope.
  • Verdicts never change ARA claim status and never replace reproduction.

Why

  • The checker cannot verify that prose matches the formal statement. Thus review is a separate, authorized record.
  • A common dataset name does not make two settings equal.
  • A small new map must not erase a contest found by a larger map.
  • Lara is Haskell. A separate process keeps the Rust workspace free of it.
  • D3: Lara is a parallel track. It joins at phase 5, so it does not block the core.

Agora

  • Agora has no argument checker.
  • Workers wrote 284 insight nodes, for example plateau diagnoses. Nobody tested them as arguments.
  • The "contested verifications" view shows disagreement about score reproduction, not argument attacks.
  • The vault lists an open question: can Lara certificates attach to Agora insight nodes?

6.9 Peer-feedback merge: one identity through two routes 04, D6

Observed with ara 0.1.23. The seed has C01. Forks A1 and B1 each add an unrelated local C77. B2 starts as a copy of B1.

OperationResult
Canonical imports B1 (base: seed)Exit 0
Canonical imports A1 (base: seed)Exit 0
B2 imports A1 (base: seed)Exit 0
Canonical imports B2 (base: B1, key fork-b)Exit 1, merge.alias_conflict on fork-a:C77. It is C03 in canonical and C78 in B2.

The claim C77 of A arrives through two routes: directly, and through B. This is a diamond import history. It is not a scientific disagreement.

What

  • Find proven original identities before the merger allocates destination IDs.
  • If an incoming entry has an origin that already exists in the destination, use that destination ID.
  • Two unrelated local C77 entries stay separate.
  • Keep immutable source facts separate from per-destination import events (base, time, local mapping).
  • If the same entry changed on both routes, give one identity and a normal mutable conflict.
  • Reject forged or ambiguous aliases and protected-history edits before any change.
  • The runner enables native peer imports only after these tests pass.

Why

  • Workers must keep native knowledge that includes peer work. Package-only reuse avoids the bug but prevents this.
  • A new source key or dropped aliases would lose provenance.
  • Equal text or equal numbers do not prove identity. Unrelated findings can share both.
  • If the merger ignores differences in foreign history, it can hide protected-history edits.

Agora

  • Agora does not need identity reconciliation, because it does not merge.
  • Each node has one global commit hash. A node cites parents by hash. Thus a diamond import cannot occur.
  • The cost: Agora cannot combine divergent work into one reviewed document.

8. What the design takes from Agora

Taken

  • Immutable publication before integration.
  • Negative results as normal records.
  • Verification as a record with one exact target, never own work.
  • Views of open hypotheses, unverified results, and contested results.
  • A prediction before execution. Agora workers did this by convention. This design binds it to the intention.
  • Author identity on each record, separate from the provenance category.

Not taken, and why

  • A hosted service. It adds deployment, admission, storage, and network-failure contracts before the same-host loop works.
  • One Git commit for each ARA entry. ARA keeps typed files and a semantic merge.
  • A numeric ranking formula or embeddings. The briefing starts with structural facts and a versioned grouping policy.
  • Corrections only in a database. All corrections are immutable records.
  • A score that implies truth. Scores are process measures only.
Both systems share a known risk: a visible best result attracts all effort (anchoring). Agora reports one narrow spine of work. The design does not solve anchoring. It reports branch concentration and neglected branches.

11. Limits and costs

  • Nothing is implemented. The current binary (0.1.23) fails the diamond case. Native peer imports stay disabled until plan 04 passes.
  • Same host only. No network transport, hosted API, or cryptographic participant admission.
  • Storage. Snapshots, predecessor packages, and receipts use space. Large evidence must go to pinned object storage. The proposed store shares unchanged file contents between snapshots. It has no retention policy in the first release.
  • Store dependency. The jj-lib store adds crates, build time, and binary size. Its API changes often. The spike measures the cost. The fallbacks are gix behind the same trait, or the directory-only command.
