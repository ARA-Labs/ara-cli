# Issue 42: Relax Value-Recovering Fix Guards

> **Status:** Proposed; implementation requires maintainer approval.
> **Issue:** [ARA-Labs/ara-cli#42](https://github.com/ARA-Labs/ara-cli/issues/42)
> **Branch:** `bugfix/42-relax-check-fix-guard`

## Goal

Allow `ara check --fix` to apply ARA002, ARA003, and ARA004 when an artifact already has parse errors, provided the candidate removes or preserves every existing error, introduces no new error, performs only the targeted recovery, and remains idempotent.

## Background

The Stage 5 contract says a value-recovering fix is safe when it introduces no new errors and changes only the intended value or claim. The implementation is stricter:

- `guard_alias` accepts only `Ok` base and candidate parses.
- `guard_ara004` accepts only an `Ok` candidate parse.
- `parse_sources` constructs a normalized `Manifest` for most semantic errors, then discards it when returning `Err(ParseReport)`.

As a result, an unrelated duplicate id, cycle, or unknown reference prevents a safe alias rename. Multiple malformed claim headers also deadlock the fixpoint loop: fixing one header leaves errors from the remaining malformed headers, so the first candidate is rejected and no header is repaired.

This contradicts the documented safety rule and makes autofix ineffective on the real corpus. The vendored NanoGPT Speedrun artifact contains ten em-dash claim headers; its missing claims produce the unknown-claim errors that currently block their own recovery.

Implications for this fix:

1. `ara check --fix` operates on source artifacts before or independently of Hub publication. It must not edit, regenerate, or special-case `trajectory.html`.
2. A source-only header rewrite does not change an already-published Hub page until that artifact's static HTML is regenerated by the Hub pipeline.
3. The regression test should use the same vendored NanoGPT source that backs the live artifact. This proves the CLI can recover production input rather than only a synthetic shape.
4. Scope stays limited to fields already modeled by `ara-core`. The Hub's additional claim falsification data and per-node `thinking` narratives remain separate work tracked by issues #61 and #64.

## Proposed solution

### Preserve normalized manifests for guard evaluation

Refactor the private parser path in `crates/ara-core/src/parse.rs` around a crate-private outcome:

```rust
pub(crate) enum ParseOutcome {
    Normalized(Manifest, ParseReport),
    Fatal(ParseReport),
}
```

Add a crate-private `parse_sources_detailed(tree_yaml, claims_md) -> ParseOutcome` containing the existing normalization flow.

- Return `Fatal` only when no meaningful manifest can be built, such as malformed YAML or an invalid top-level root shape.
- Return `Normalized(manifest, report)` after normalization even when `report` contains semantic errors such as duplicate ids, cycles, or unknown references.
- Keep the public `parse_sources` signature and behavior unchanged: a normalized outcome with errors still maps to `Err(ParseReport)`, and `ara validate` output remains byte-stable.
- Do not expose partial manifests through the public API.

This keeps one parser implementation, avoids reparsing or copying source fragments, and lets safety guards inspect the same normalized state that produced the diagnostics.

### Relax only value-recovering guards

In `crates/ara-core/src/fix.rs`, parse the base and candidate through `parse_sources_detailed` and apply these rules:

- **ARA001:** unchanged. Both parses must be error-free normalized manifests, and the manifests must be identical.
- **ARA002/ARA003:** require normalized base and candidate manifests; require the candidate error multiset to be a subset of the base error multiset; then retain the current proof that exactly one target field changes from `None` to `Some` and clearing it reproduces the base manifest.
- **ARA004:** require normalized base and candidate manifests; require the candidate error multiset to be a subset of the base error multiset; retain the current header/id/title checks; require the candidate claim list minus the recovered claim to equal the base claim list; require nodes and links to remain identical; and require candidate bindings minus bindings to the recovered claim to equal the base bindings.
- **Fatal base or candidate:** reject the fix and leave the source byte-identical.

Diagnostic containment uses full identity (`severity`, logical path, and message) and preserves occurrence counts. If the base has one copy of an error and the candidate has two identical copies, the candidate is not a subset. An equal count with a different error is also unsafe.

```text
raw tree + claims
        │
        ├── parse_sources_detailed(base) ── Fatal ───────────────┐
        └── parse_sources_detailed(candidate) ── Fatal ──────────┤
                                                                 ▼
                                                       reject; write nothing

Normalized(base, report) + Normalized(candidate, report)
        │
        ├── ARA001: both reports clean + manifests identical
        │
        └── ARA002/003/004:
              candidate errors ⊆ base errors  (multiset)
                          +
              exact rule-specific manifest delta
                          +
              candidate drift eliminated on re-check
        │
        ├── reject ───────────────────────────────► source byte-identical
        └── accept ─► update in memory ─► re-detect ─► write changed file once
```

## NOT in scope

- Do not relax ARA001's semantic-no-op requirement.
- Do not suppress, downgrade, or rewrite pre-existing diagnostics.
- Do not modify `ara validate` output or the public parser contract.
- Do not add tolerant aliases to serde; the canonical source rewrite remains explicit and visible.
- Do not modify the local viewer, production Hub, `trajectory.html`, or Hub ingestion.
- Do not add claim falsification or node narrative fields under this issue.
- Do not widen the parser to the complete real-corpus schema (`T-REAL-CORPUS`); issue 42 uses the existing normalized model.
- Do not add parser recursion-depth hardening (`T-PARSE-DEPTH`); it is independent of fix-guard correctness.
- Do not add a synthetic performance benchmark; the parser count and asymptotic fixpoint cost are unchanged, and the vendored corpus smoke test covers observed scale.

## What already exists

- `parse_sources` already performs the only normalization pass and constructs the complete core `Manifest`; the plan retains its internal result instead of building a second tolerant parser.
- `fix_dir` already owns the detect → candidate → guard → re-detect fixpoint, single-write behavior, skipped-fix reporting, and idempotence backstop; the plan changes only guard inputs and proofs.
- `errors_subset` already expresses the intended direction of diagnostic containment; the plan corrects it to occurrence-aware multiset semantics.
- Existing `fix.rs` tests cover clean ARA001/002/003/004 application, multi-node alias rejection, write failures, combined fixes, and second-run idempotence.
- The vendored NanoGPT fixture already supplies production-shaped input with attribution and hermetic test availability.

## Failure modes

| Failure | Guard / handling | Coverage | User-visible result |
|---------|------------------|----------|---------------------|
| Base or candidate has no meaningful manifest | Reject any value-recovering candidate before semantic comparison | Fatal alias and ARA004 unit regressions | Fix remains listed as skipped; source is byte-identical |
| Candidate adds a different error | Candidate error multiset is not a subset of base | Same-sized/different-diagnostic regression | Fix skipped; original diagnostic state remains |
| Candidate adds another copy of an existing error | Occurrence-aware matching fails | Duplicate-count regression | Fix skipped; source is byte-identical |
| Recovered claim introduces an unknown dependency | New dependency diagnostic fails containment | ARA004 negative regression | Fix skipped rather than creating a new validation error |
| ARA004 perturbs unrelated bindings | Exact binding subtraction fails | Binding-delta guard regression | Fix skipped; no unrelated semantic change reaches disk |
| Filesystem write fails after an accepted in-memory edit | Existing `FixOutcome.errors` path reports the failure and does not mark the file changed | Existing Unix write-failure test | CLI surfaces an internal failure instead of reporting clean |
| Version bump leaves a stale lockfile | Final gates use `--locked` after `cargo build` refreshes `Cargo.lock` | Required PR gate sequence | CI/local gate fails before review or merge |

No failure mode is silent and uncovered.

## Parallelization strategy

Sequential implementation, no parallelization opportunity. Parser outcome extraction and guard changes share `ara-core` types and tests; CLI regressions depend on the finalized core behavior; documentation, versioning, lockfile refresh, and final gates follow the functional implementation. Splitting these across worktrees would create coordination and merge cost without an independent lane.

## Acceptance criteria

- `ara check --fix` repairs all ten NanoGPT Speedrun claim headers on a copy and clears the unknown-claim errors caused by those headers.
- ARA002 and ARA003 apply despite unrelated semantic errors when the candidate error multiset is a subset of the base multiset.
- No applied fix introduces a new error occurrence, including an extra copy of an otherwise identical diagnostic.
- ARA004 adds exactly one recovered claim plus only bindings to that claim; unrelated nodes, links, claims, and bindings remain unchanged.
- Targeted semantic-delta checks remain mandatory; fatal or ambiguous parses are still rejected.
- Rejected fixes leave files byte-identical.
- A second `--fix` run is a no-op.
- `ara validate` output and the public `parse_sources` contract remain unchanged and are protected by exact characterization coverage.
- Native and wasm PR gates pass against the final `Cargo.toml` and refreshed `Cargo.lock`.
- The production Hub rendering pipeline and generated `trajectory.html` remain untouched.
