# Issue 42: Relax Value-Recovering Fix Guards

> **Status:** Proposed; implementation requires maintainer approval.
> **Issue:** [ARA-Labs/ara-cli#42](https://github.com/ARA-Labs/ara-cli/issues/42)
> **Branch:** `bugfix/42-relax-check-fix-guard`

## Goal

Allow `ara check --fix` to apply ARA002, ARA003, and ARA004 when an artifact already has parse errors, provided the candidate removes or preserves every existing error, introduces no new error, performs only the targeted recovery, and remains idempotent.

## Background

The Stage 5 contract says a value-recovering fix is safe when it introduces no new errors and changes only the intended value or claim. The implementation is stricter:

- `guard_alias` accepts only `Ok` base and candidate parses.
- `guard_ara004` accepts only an `Ok` candidate parse.
- `parse_sources` constructs a normalized `Manifest` for most semantic errors, then discards it when returning `Err(ParseReport)`.

As a result, an unrelated duplicate id, cycle, or unknown reference prevents a safe alias rename. Multiple malformed claim headers also deadlock the fixpoint loop: fixing one header leaves errors from the remaining malformed headers, so the first candidate is rejected and no header is repaired.

This contradicts the documented safety rule and makes autofix ineffective on the real corpus. The vendored NanoGPT Speedrun artifact contains ten em-dash claim headers; its missing claims produce the unknown-claim errors that currently block their own recovery.

- Artifact page: <https://www.agenticresearch.sh/ara/AmberLJC/ara-paperbench/artifacts/speedrun/nanogpt-speedrun>

- Source artifact: <https://github.com/AmberLJC/ara-paperbench/tree/main/artifacts/speedrun/nanogpt-speedrun>

The production artifact page does not parse the raw ARA on each view. It fetches the repository's prebuilt `trajectory.html` through jsDelivr and places the self-contained HTML in a sandboxed iframe via `srcdoc`. That HTML contains fixed renderer code plus an injected `ARA_DATA` JSON object. For this artifact, the embedded object contains 28 nodes and per-node claim cards; C01 is present with its title, statement, status, and falsification criterion even though the source `logic/claims.md` uses `## C01 — ...`.

Implications for this fix:

1. `ara check --fix` operates on source artifacts before or independently of Hub publication. It must not edit, regenerate, or special-case `trajectory.html`.
2. A source-only header rewrite does not change an already-published Hub page until that artifact's static HTML is regenerated by the Hub pipeline.
3. The regression test should use the same vendored NanoGPT source that backs the live artifact. This proves the CLI can recover production input rather than only a synthetic shape.
4. Scope stays limited to fields already modeled by `ara-core`. The Hub's additional claim falsification data and per-node `thinking` narratives remain separate work tracked by issues #61 and #64.

## Proposed solution

### Preserve normalized manifests for guard evaluation

Refactor the private parser path in `crates/ara-core/src/parse.rs` around a crate-private outcome:

```rust
pub(crate) enum ParseOutcome {
    Normalized(Manifest, ParseReport),
    Fatal(ParseReport),
}
```

Add a crate-private `parse_sources_detailed(tree_yaml, claims_md) -> ParseOutcome` containing the existing normalization flow.

- Return `Fatal` only when no meaningful manifest can be built, such as malformed YAML or an invalid top-level root shape.
- Return `Normalized(manifest, report)` after normalization even when `report` contains semantic errors such as duplicate ids, cycles, or unknown references.
- Keep the public `parse_sources` signature and behavior unchanged: a normalized outcome with errors still maps to `Err(ParseReport)`, and `ara validate` output remains byte-stable.
- Do not expose partial manifests through the public API.

This keeps one parser implementation, avoids reparsing or copying source fragments, and lets safety guards inspect the same normalized state that produced the diagnostics.

### Relax only value-recovering guards

In `crates/ara-core/src/fix.rs`, parse the base and candidate through `parse_sources_detailed` and apply these rules:

- **ARA001:** unchanged. Both parses must be error-free normalized manifests, and the manifests must be identical.
- **ARA002/ARA003:** require normalized base and candidate manifests; require `errors(candidate) ⊆ errors(base)`; then retain the current proof that exactly one target field changes from `None` to `Some` and clearing it reproduces the base manifest.
- **ARA004:** require normalized base and candidate manifests; require `errors(candidate) ⊆ errors(base)`; retain the current header/id/title checks; require the candidate claim list minus the recovered claim to equal the base claim list; require nodes and links to remain identical.
- **Fatal base or candidate:** reject the fix and leave the source byte-identical.

The comparison uses full diagnostic identity (`severity`, logical path, and message), not only the error count. An equal count with a different error is not safe.

## Non-goals

- Do not relax ARA001's semantic-no-op requirement.
- Do not suppress, downgrade, or rewrite pre-existing diagnostics.
- Do not modify `ara validate` output or public parser behavior.
- Do not add tolerant aliases to serde; the canonical source rewrite remains explicit and visible.
- Do not modify the local viewer, production Hub, `trajectory.html`, or Hub ingestion.
- Do not add claim falsification or node narrative fields under this issue.

## Acceptance criteria

- `ara check --fix` repairs all ten NanoGPT Speedrun claim headers on a copy and clears the unknown-claim errors caused by those headers.
- ARA002 and ARA003 apply despite unrelated semantic errors when their candidate error set is a subset of the base set.
- No applied fix introduces a new error diagnostic.
- Targeted semantic-delta checks remain mandatory; fatal or ambiguous parses are still rejected.
- Rejected fixes leave files byte-identical.
- A second `--fix` run is a no-op.
- `ara validate` output and the public `parse_sources` contract remain unchanged.
- The production Hub rendering pipeline and generated `trajectory.html` remain untouched.
