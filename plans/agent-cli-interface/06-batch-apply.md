## TL;DR

Add `ara apply ops.jsonl` as one in-memory plan and one guarded transaction, with creation bindings and a dry run that leaves source files unchanged. Reuse the individual commands' library operations. Complete the knowledge-layer writes required by the pinned compiler and manager, including mutable logic bodies, PAPER metadata/index text, full revision history, reasoning/taste records, and initialization after their scope decisions are approved. Consume PR 12's machine-readable inventory and block skill integration on every uncovered required operation. Passing node-batch tests does not establish compiler coverage.

## Problem

The parent names a compiler workflow that replaces many direct file writes with `ara apply`. PRs 03 through 05 cover nodes, selected fields, staging, promotion, and sessions, but the current compiler also creates `logic/problem.md`, concepts, experiment plans, related work, constraints, and whichever solution documents the source warrants. It creates PAPER frontmatter and a layer index that the current `PaperMeta` does not fully model. The current manager requires reasoning notes, optional taste comments, stale handling, non-claim promotions, structural logic changes, and complete before/after revision records.

Without an explicit access inventory, an implementation could pass its node-batch tests while copied skills still need direct knowledge-file edits. PR 12 proposes `evaluation/agent-cli/operation-coverage.json` in the protocol repository, version `ara.skill-operations/v1`, with pinned skill revision/hash, source clause, native selector, read/write access, required payload/history/provenance, proposed operation tag, coverage proof, and blocked reason. This PR consumes that exact reviewed artifact. Its final required operation list follows the pinned inventory rather than the current unpinned local skill snapshot.

## Constraints

Run no LLM, network request, external skill subprocess, or per-operation `ara` subprocess inside `apply`. Resolve references and allocate IDs in one locked working snapshot; commit no source files until the entire batch passes syntax, reference, intent, and protocol checks. Code bodies, raw evidence, screenshots, and execution remain direct skill access under the parent's non-goals. Required knowledge writes cannot fall back to Write/Edit on failure. A newly discovered operation or permission that changes scope requires an explicit approval decision before this PR or PR 13 ships.

Batch JSON strings are literal UTF-8 content, including strings beginning with `@`; shell `key=@file` syntax does not apply inside JSON. `ara apply -` consumes JSONL from stdin, so embedded stdin field inputs are prohibited. An empty line is ignored; blank-only input is a documented no-op. Reject malformed JSON, unknown tags/fields, invalid types, duplicate JSON object keys, and multiple operations packed into one JSONL line. Errors include the 1-based line, operation tag when known, and logical field path. Review limits for input size before publishing the API; do not invent an undocumented truncation policy.

## Proposed approach

Add `crates/ara-core/src/write/batch.rs`, `documents.rs`, and `records.rs` (new, native-only), and `crates/ara-cli/src/apply.rs` (new). Extend the shared operation enum and source-policy registry, session/staging operations from PR 05, field operations from PR 04, and native readers/query source selectors where coverage requires them. `parse_batch(bytes) -> Vec<WriteOperation>` performs strict input parsing. `execute(root, operations, ApplyMode::Commit | ApplyMode::DryRun)` takes one checkout lock and returns `WriteReport`; both modes use the same `WorkingArtifact`, intents, allocation, and final validation.

The initial union includes `node.add`, `edge.add`, `claim.add`, `heuristic.add`, `entry.edit`, `observation.stage`, `observation.promote`, `session.start`, and `session.log`, using the exact payloads in PRs 03 through 05. Creation operations may use `"id":"$a"` to bind an assigned native ID. A binding is unique, type-checked, and visible only to later operations. Reject duplicate, unknown, forward, or wrong-kind bindings. Only structured reference fields substitute `$` values; ordinary prose and source quotes remain literal. Concrete stored IDs and requested replay IDs retain the protocol grammar. Dry-run IDs and session turns are tentative and may change before a later commit.

```jsonl
{"op":"node.add","id":"$a","type":"question","parent":"root","title":"Boundary question","fields":{"provenance":"user"},"depends_on":[]}
{"op":"node.add","id":"$b","type":"experiment","parent":"$a","title":"Boundary experiment","fields":{"provenance":"ai-executed","result":"Observed boundary"},"depends_on":[]}
{"op":"observation.stage","id":"$o","content":"Interpretation to review","potential_type":"claim","context":"After the experiment","provenance":"ai-suggested","timestamp":"2026-10-01T10:00","bound_to":["$b"]}
```

Additional operation shapes below are proposals requiring the inventory and protocol review. `document.create` creates an absent allowlisted knowledge document with the caller's complete content. `document.replace` changes an existing mutable document or explicit heading body and requires an `expected` source digest. The intent declares the whole selected body as changed, while unrelated bodies and unknown PAPER frontmatter remain intact. `record.append` is typed by document/record kind and can only append a valid record. `logic.revise` couples a mutable change, its exact trace before/after history, and the required revision pointer in one operation. `artifact.init` uses an explicit root and a reviewed seed profile; it is not a generic filesystem writer.

```json
{"op":"document.create","document":"logic/solution/algorithm.md","content":"# Algorithm\n\nComplete source-grounded method.\n"}
{"op":"document.replace","document":"logic/problem.md","heading":["Assumptions"],"expected":"sha256:<source-body-digest>","content":"Complete replacement body.\n"}
{"op":"paper.edit","frontmatter":{"claims_summary":["C01"]},"heading":["Layer Index"],"expected":"sha256:<source-index-digest>","content":"Complete layer-index body.\n"}
{"op":"record.append","document":"trace/pm_reasoning_log.yaml","record":{"turn":"2026-10-01_001#1","notes":["Recorded the caller's routing decision."]}}
{"op":"record.append","id":"$taste","document":"trace/taste_log.yaml","record":{"timestamp":"2026-10-01T10:01","target":"N12","tag":"uncertain","object":"framing","comment":"Caller-confirmed reaction."}}
{"op":"logic.revise","target":{"id":"C05"},"set":{"Statement":"New wording"},"session":"2026-10-01_001","turn":1,"signal":"user-directive","provenance":"user-revised","note":"Caller requested a narrower scope"}
{"op":"artifact.init","profile":"research-manager","paper":"Complete caller-supplied PAPER.md content"}
{"op":"entry.rename","target":{"document":"logic/concepts.md","heading":["Old term"]},"name":"New term","expected":"sha256:<source-entry-digest>","references":[{"target":{"id":"C05"},"field":"Statement","before":"Old term applies","after":"New term applies"}]}
{"op":"entry.remove","target":{"document":"logic/experiments.md","entry":"E03"},"expected":"sha256:<source-entry-digest>","references":[]}
{"op":"entry.taste_append","target":{"id":"C05"},"record":{"date":"2026-10-01","tag":"uncertain","object":"framing","comment":"Caller-confirmed reaction."}}
{"op":"entry.annotate","target":{"id":"C05"},"kind":"conflict","references":["C06"],"comment":"Unresolved contradictory evidence"}
{"op":"artifact.init","profile":"compiler","documents":{"PAPER.md":"Complete caller-supplied root document","logic/problem.md":"Complete problem body","logic/claims.md":"Complete claims body","logic/concepts.md":"Complete concepts body","logic/experiments.md":"Complete plans body","logic/related_work.md":"Complete related-work body","logic/solution/constraints.md":"Complete constraints body"}}
```

Document targets include the pinned logic core and content-warranted `logic/solution/*.md`, using real filenames and heading paths rather than invented IDs. Support whole mutable document replacement when explicitly requested, but do not reserialize a document from `Manifest`. Structural create/remove/rename of mutable entries requires typed intents that preserve all other source blocks and validate every affected reference; it cannot silently delete trace entries. Experiment plans retain `E` headings, related work retains `RW`, and concepts retain term names. PAPER operations cover approved frontmatter fields including metadata the normalized `PaperMeta` drops, plus complete overview/index bodies. New field permission or schema conflicts are recorded as approval blockers, not treated as already-supported fields.

Root `PAPER.md` writes and artifact initialization exceed the parent's named trace/staging/logic write boundary. They are necessary candidate extensions for compiler coverage, but require explicit parent-scope and protocol approval before implementation. If approval is withheld, keep their inventory rows blocked and do not ship integrated compiler copies. Initialization may create empty `src/` and evidence directories as structure, but their content remains direct skill work; evidence indexes also need an explicit boundary decision rather than a generic writer exception.

Complete read access is part of the coverage gate. Extend the native read adapter with proposed `ara show --document <allowed-path> [--heading <component> ...] --source --full` to return exact document or section text, including unknown fields, and its source digest. The JSON result retains `ara.show/v1` and adds a source-document variant with document, selector, content, and digest; review that additive result before publication. Structured queries still use PR 01's normalized model, while source retrieval uses PR 03's lossless snapshot. No arbitrary path outside the reviewed knowledge boundary is readable through this variant. Without this surface, copied skills cannot inspect whole logic bodies or read-modify-write unknown PAPER content faithfully.

## Alternatives considered

Calling one command per JSONL line duplicates process startup and cannot provide all-or-none behavior. Parsing a batch directly into arbitrary file replacement instructions avoids operation work but bypasses mutability and history rules. Use the shared library planners and typed union.

A smaller batch release with only node operations is useful but cannot satisfy the parent's compiler/manager migration promise. If the reviewed inventory reveals additional substantial work, approve extra scoped PRs and keep PR 13 blocked until they land. Do not silently narrow this PR's acceptance or call partial coverage complete.

## Tradeoffs

Batches retain complete source candidates and history in memory, so large compilations cost more memory than one append. Measure representative batches before adding caching or streaming commits that would weaken rollback. Dry-run predictions can become stale once the lock is released; their IDs and digests are a preview, not a reservation.

The source paths stay conventional, which limits atomic visibility to cooperating readers. Each file rename is atomic, but raw readers can observe partial multi-file commits. Ordinary rollback uses PR 03's contract, with explicit errors when restoration fails; crash durability arrives with PR 08's journal. No success response should imply that code/evidence writes outside the knowledge transaction were atomic with it.

## Migration

Existing single-write commands continue to call the same operation planners; there are no subprocess shims or a second write policy. PR 12 preserves the original file-based skills. PR 13 adds CLI-only variants only after the reviewed coverage artifact has no uncovered required knowledge operation and the full fidelity scenarios pass. The current local compiler/manager files are design evidence, not a verified experiment pin. Unapproved field grammar and session/stale/history choices remain explicit release blockers.
